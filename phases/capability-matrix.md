# Cert-Lifecycle-Harness · 能力矩阵（Capability Matrix）

> 本文件是 Skill **能力边界的书面契约**。
> 每一次对 `SKILL.md` 的能力增删，**必须同步更新本文件**，以防 Skill 在推演/补齐过程中**向具体案例悄悄倾斜**而偏离原始能力定义。
>
> 矩阵本身不是"Skill 能做什么"的清单，而是 **"Skill 在哪些维度取值上声明了能力 / 明示不支持"** 的对照表。
> 反审时只比对 **Skill 声明**与 **SKILL.md 的落地内容**是否一致；**不做能力完备性审查**（那属于未来路线图，不属于骨架阶段）。

### 1.2 本 Skill **明确声明不支持**的能力（边界外）

| 不支持 | 原因 |
|-------|------|
| Agent 代为执行 **Delete 类**写操作 | 难回滚，CT 日志留痕，风险不对称 |
| Agent 自动审批 review 通过 | 权力必须留在人类侧 |
| Agent **ssh 进生产** / 改生产配置文件 | 不在授权模型内 |
| Agent 在**未授权**时调 cloud API | 违反授权协议 |
| Agent 用**自己的知识脑补**客户特定信息 | § 2 硬约束 |
| Agent 把**推荐**当事实写入 L2/L1 交付物（未经用户确认） | § 2.1 硬边界 |
| Agent **持久化凭证**到任何文件 | § 0.1 硬边界 |

### D6 · DNS 掌控权（v0.3 新增）

> DNS 是证书场景里的"基础设施反向探针"。同一家客户的 DNS 记录、云资源、CDN 接入**常常分离在不同厂商**（例：DNS 在 GoDaddy，资源在腾讯云），不能并入 D1 基础设施形态，也不能并入 D4 授权深度，因此升为独立维度。

| 取值 | 是否纳入声明 | SKILL.md 锚点 | Agent 可做什么 |
|------|------------|--------------|----------------|
| D6.a 无 DNS 授权 | ✅ | § 5 Phase 1 分支 B | 仅靠用户问卷 + 本地 `dig`，信息最弱 |
| D6.b 一次性记录提供（zone export / CSV） | ✅ | § 5 Phase 1 分支 B | Agent 做**一次性基础设施反推**：由 CNAME / CAA / NS / TXT 推断 CDN、源站、CA 偏好、ACME 现状 |
| D6.c DNS 只读 API 授权 | ✅（默认推荐） | § 0.1 只读行；§ 5 Phase 1 分支 A | Agent 做**持续探测、漂移发现**；探针作用域严格受限于证书 SAN 范围（N2′ 原则） |
| D6.d DNS 读写 API 授权 | ❌ **当前不纳入** | § 0.2 Delete / 写闸门外 | ACME DNS-01 等写操作**不代执行**，仅生成脚本交人类（A3 决策）|

**D6 特有硬边界**（对应 SKILL.md § 0.1 DNS 探针小节）：
- **作用域限定**：Agent 查询范围 = 证书 SAN 清单 + 通配符展开范围 + 直接父域（查 CAA 用）
- **明示推理**：每一次由 DNS 记录反推出的基础设施事实，都必须以"证据 + 推断 + 请确认"形式呈现给人类，不做隐式决策
- **隐私自律**：就算持有全 zone 只读权限，也不主动列无关子域（如 `hr.*` / `finance.*` / `internal.*`）

## 3. 组合严格度规则（决策 4B：分级反审）

反审时按组合的**实际发生频率**分级标色，避免对低频场景过度要求：

| 频率分级 | 定义 | 反审标色 | 处理 |
|---------|------|---------|------|
| **高频** | 行业内 ≥60% 的证书更换场景会涉及 | 🔴 红 | 必须在骨架/模板补齐阶段覆盖，无支撑即缺项 |
| **中频** | 行业内 10-60% 场景会涉及 | 🟡 黄 | 骨架可缺，但需在 `phases/` 或 `review-guides/` 明示"待推演确认" |
| **低频** | 行业内 <10% 场景才涉及 | ⚪ 白 | 不反审；需要时走专项推演补齐 |

### 3.1 高频组合（🔴 红：骨架必须覆盖）

| # | 组合（D1 × D2 × D3 × D4 × D5） | 频率判据 |
|---|--------------------------|---------|
| H1 | 公有云（含混合） × 商业 DV/OV × 中等拓扑 × 只读+Modify × 无合规 | 互联网公司主流泛域名更换 |
| H2 | 混合 × 商业 DV × 复杂拓扑 × 只读+Modify × 无合规 | SaaS / 大型互联网，CDN+LB+K8s |

## 4. 矩阵与 SKILL.md 的同步规则

### 4.1 何时必须更新本文件

| 变更类型 | 是否必须更新本文件 |
|---------|------------------|
| 对 `SKILL.md` 新增能力声明 | ✅ 必须在 §1.1 新增一行；并检查 §2 矩阵是否有新维度/取值 |
| 对 `SKILL.md` 删除/收窄能力 | ✅ 必须在 §1.2 新增一行，并在 §2 矩阵中把对应取值改为 ❌ |
| 对 `SKILL.md` 只做措辞澄清 | ⚪ 不需要更新，但建议在 `updated` 字段刷新日期 |
| 新增 `phases/` 或 `review-guides/` 模板 | ✅ 若模板落地了 §1.3 列出的"明示未落地"能力，把对应行从 §1.3 移除 |
| 通过推演发现新的能力需求 | ✅ 先在本文件 §5 "待决定的能力边界"登记，走人类决策后再写入 §1.1 或 §1.2 |

### 4.2 反审工作流

```
Step 1: 以 §2 矩阵为底图，逐行扫 SKILL.md 实际支撑
Step 2: 按 §3 分级规则标色
Step 3: 输出《声明兑现缺项报告》：
        - 🔴 红项 → 阻断式缺项，必须在下一阶段补齐
        - 🟡 黄项 → 需在 phases/ 或 review-guides/ 明示"待推演确认"
        - ⚪ 白项 → 不写入报告
Step 4: 报告**只给事实，不自动改 SKILL.md**；由人类决定补齐优先级
```

### 4.3 反审不做的事

- ❌ 不做"能力是否该加"的价值判断（那是产品决策）
- ❌ 不做"某个云的 API 对不对"的校验（Skill 不绑定厂商）
- ❌ 不替用户决定补齐顺序
